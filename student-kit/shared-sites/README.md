# Один родительский блок, много дочерних сайтов

```
родительский репозиторий: исходник блока + контракт настроек
                         ↓ release commit SHA
дочерний репозиторий A: pin + данные страницы + допустимые настройки
дочерний репозиторий B: pin + свои данные + допустимые настройки
                         ↓ build → проверка → публикация
```

В системе AI Mindset общий header/footer принадлежит родительскому репозиторию блоков. Дочерний сайт фиксирует **конкретный commit SHA** родителя в `platform-dependency.json`, а свой текст и разрешённые настройки хранит отдельно. Изменение родителя само по себе не меняет опубликованные сайты: каждый потребитель обновляет pin, собирается, проверяется и выпускается отдельно.

## Файлы этого примера

- [`platform-dependency.example.json`](platform-dependency.example.json) — запись точной версии родителя. SHA здесь учебный, его нужно заменить реальным 40-символьным SHA.
- [`page.example.json`](page.example.json) — данные экземпляра: заголовок, тема, CTA и список блоков. Это не копия родительского header/footer.
- [`contract.example.json`](contract.example.json) — список допустимых настроек и обязательных узлов, который должен проверять рендерер родителя.

## Как собрать свою схему

1. В **parent repo** храните один исходник компонента, схему настроек, тесты и инструкцию для потребителя. Определите, какие части обязательны, а какие можно менять на уровне страницы.
2. Выпустите commit родителя. Зафиксируйте его SHA, не плавающую ветку `main`.
3. В **child repo** добавьте pin и конфигурацию страницы. Рендерер должен читать родителя на указанном SHA и отклонять неизвестные настройки, пропавшие mount-узлы и несовместимую версию контракта.
4. Собирайте HTML из исходных файлов. Сгенерированный HTML считайте результатом сборки, а не местом ручных правок.
5. Проверьте десктоп, телефон, ссылки, фокус с клавиатуры, обязательные пункты меню и читаемость выбранной темы. Затем опубликуйте конкретную сборку и запишите SHA родителя рядом с ней.
6. Для следующего изменения повторите обновление pin и проверку в каждом дочернем сайте. Откат — возвращение к предыдущему пину и публикация прежней проверенной сборки.

Если общий блок доставляется через [повторно используемый workflow GitHub Actions](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows), зафиксируйте версию workflow и права вызывающего репозитория отдельно. CI может проверять контракт и собирать артефакт; право на публикацию должно оставаться явным.

## Что может менять студент

Название страницы, контент, разрешённые варианты темы, локальный CTA и порядок своих блоков. Глобальная навигация, юридические ссылки, базовая семантика и механика доступности остаются у владельца родителя. Если нужно новое поведение общего блока, предложите изменение в parent repo, а затем обновите pin потребителей.

**Не подменяйте** общий компонент копией HTML/CSS в дочерней странице: тогда исправления родителя перестанут доходить до неё. Не считайте одинаковые CSS-числа доказательством одинакового визуального результата — проверьте отрисовку на нужных размерах.
