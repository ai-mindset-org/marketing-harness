# QA-дашборд для страниц

Это небольшой статический пример отчёта по нескольким страницам. Он использует **синтетический** [`report.example.json`](report.example.json) и показывает сводку, проблемы и момент проверки. В AI Mindset изученный Site Agent Evaluation делает похожую цепочку: проверки формируют `report.json`, генератор создаёт страницы обзора и историю. Здесь нет подключения к действующему агенту или его данным.

## Посмотреть

Из корня репозитория запустите локальный статический сервер на свободном порту, ограничив раздачу папкой `student-kit/`:

```bash
python3 -m http.server 4750 --bind 127.0.0.1 --directory student-kit
```

Откройте `http://127.0.0.1:4750/qa-dashboard/`. Для просмотра на телефоне в той же сети можно отдельно запустить сервер, ограниченный папкой `student-kit/qa-dashboard/`, с `--bind 0.0.0.0`; не раздавайте весь рабочий репозиторий в локальную сеть.

## Подключить к своему сайту

1. Определите список страниц, размеры экранов, проверки и ответственного за каждый сигнал.
2. Пусть агент выдаёт отчёт **по схеме**: `generatedAt`, `sourceRevision`, `sites[]`, `checks[]`. Для каждого check нужны `status`, короткое описание и ссылка на доказательство или её отсутствие.
3. Перед публикацией отчёта уберите персональные данные, закрытые URL, токены, скриншоты внутренних интерфейсов и контактные формы с реальными данными.
4. Генерируйте статический отчёт после каждой проверки, сохраняйте историю с датой и исходным commit SHA. Ошибка сборки или отсутствие отчёта должны быть отдельным сигналом.
5. Публикуйте только после проверки прав доступа. Дашборд показывает выводы проверок; он не заменяет просмотр человеком на десктопе и телефоне.

Полезный порядок для первой версии: ручной запуск → один синтетический отчёт → автоматическая проверка по расписанию → сохранение истории → алерт владельцу при `fail` и при пропавшем запуске. Если используется GitHub Actions, настройте разрешения workflow и источник публикации отдельно.

## Смысл статусов

- `pass` — проверка прошла в указанном запуске;
- `warn` — сигнал требует просмотра, но не объявлен блокирующим;
- `fail` — найденная проблема;
- `unknown` — проверка не дала достоверного результата.

Старый зелёный отчёт не доказывает текущее состояние живого сайта. Всегда показывайте дату проверки и ревизию источника.
