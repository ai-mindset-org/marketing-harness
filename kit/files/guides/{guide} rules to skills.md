# от правила к скиллу

Правило говорит, что действует всегда. Скилл говорит, как сделать одну задачу, и подгружает нужные правила ссылками. Конвейер текстов держится на этой связке: агент открывает скилл, скилл ведёт по правилам, проверки ловят отклонения.

## цепочка на примере поста LinkedIn
```
{context} voice  ─┐
{rule} anti-slop ─┼→ {skill} linkedin-post → {skill} content-factory → outputs/ → check.mjs → slop-check
{rule} creative-codes ┘
```
1. **[[{rule} creative-codes]]** даёт хук и код `P-H-A-F`. Шаг 2 скилла [[{skill} linkedin-post]] требует хук из этого файла, первые две строки до 210 знаков.
2. **[[{context} voice]]** задаёт лицо, длину и регистр канала: LinkedIn – «я» автора, 900–1500 знаков, обычный регистр.
3. **[[{rule} anti-slop]]** превращается в проверку: код ищет стоп-конструкции, критик оценивает пять осей ([[{skill} slop-check]]).
4. **[[{skill} linkedin-post]]** собирает всё в порядок шагов для одной задачи.
5. **[[{skill} content-factory]]** вызывает `linkedin-post` для каждого нуклеуса, потом гонит пачку через `node bin/check.mjs` и `slop-check`, дизайнер рендерит превью.

Автор читает скилл и получает правила по ссылкам. Сами правила в тексте скилла не дублируются: правка в `rules/` доходит до всех скиллов сразу ([[{rule} principles]], пункт 3).

## когда что писать
| ситуация | слой | пример |
|---|---|---|
| ограничение действует на любой текст | правило | запрет длинного тире, коды креатива |
| задача повторяется и у неё есть порядок шагов | скилл | пост LinkedIn, раскадровка |
| нужна возможность с настройкой и проверкой одной командой | инструмент | Exa, Apify, LinkedIn API |
| ограничение можно проверить | eval | `node bin/check.mjs`, golden set |

Сомнение решается вопросом: «нужно ли это в тексте, который пишется без этого скилла?». Да – правило. Нет – скилл. Порядок в [[{skill} harness-evolve]], шаг 1.

## шаблон скилла
Файл `skills/{skill} <имя>.md`, frontmatter только `name` и `description`:
```
---
name: <имя>
description: Use when <ситуация>. Триггеры – <слова, которыми человек просит задачу>.
---
# <имя>

<одна строка: что делает и на каком правиле стоит>

1. вход: какие файлы читает
2. шаги по одному действию, у шага проверяемый результат
3. проверки: `node bin/check.mjs`, отдельный критик
4. выход: имя файла по [[{rule} naming]] и папка
5. ссылки: правила, инструменты, соседние скиллы
```
Длина 20–40 строк. Ссылки на правила в теле скилла подгружают их, description помогает агенту выбрать скилл. После правки `node bin/sync-skills.mjs`, иначе зеркала `.claude/skills` и `.agents/skills` устареют.

## как проверить, что скилл соблюдает правила
1. Добавь в [[{eval} golden-set]] один хороший и один плохой текст этого типа: хороший должен пройти проверки, плохой упасть на конкретном правиле.
2. Запусти скилл на нуклеусе из `nuclei/` и получи черновик.
3. `node bin/check.mjs` на черновике и `node bin/check.mjs --golden` на наборе эталонов.
4. Отдай черновик критику в отдельном контексте ([[{skill} slop-check]]). Балл 80 и выше – скилл принят.
5. Провалился на правиле, которого нет в шагах, – добавь ссылку на правило в шаг скилла. Провалился на новой ошибке – строка в `rules/` и отрицательный пример в golden set (ошибка дважды – правило).
6. Правка скилла или правила принимается, когда все эталоны ведут себя как раньше ([[{rule} evals]], правило 3).

Проверку раз в месяц повторяет [[{skill} harness-principles]].
