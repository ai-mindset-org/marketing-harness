# онтология харнесса

Онтология отвечает на два вопроса: из каких видов сущностей состоит папка и как они ссылаются друг на друга. Сущность – файл. Вид сущности читается по `{типу}` в имени и по папке. Связь – ссылка внутри файла. Из этих ссылок инструмент строит граф, а агент по ним находит, что править вместе.

## 12 типов сущностей
| тип | папка | что это | пример из набора |
|---|---|---|---|
| source | `sources/` | сырьё с датой и правами использования | [[{source} kumar creative machine – 2026-09-23]] |
| nucleus | `nuclei/` | одна проверяемая мысль из источника | [[{nucleus} n02 fake winner]] |
| output | `outputs/` | черновик или рендер для канала | [[{post} li-01 fake winner]] |
| rule | `rules/` | ограничение, которое действует всегда | [[{rule} anti-slop]] |
| skill | `skills/` | рецепт одной задачи | [[{skill} linkedin-post]] |
| tool | `tools/` | возможность с настройкой и проверкой | [[{tool} exa]] |
| role | `roles/` | кто решает, пишет, принимает | [[{role} marketer]] |
| automation | `automations/` | рутина по расписанию | [[{automation} weekly loop]] |
| gate | `gates/` и `bin/` | остановка, которую проверяет код | [[{gate} human publishes]] |
| eval | `evals/` | рубрика, эталоны, отчёты проверок | [[{eval} golden-set]] |
| dashboard | `dashboards/` | срез состояния за неделю | [[{dashboard} weekly – 2026-09-29]] |
| design | `design/` | токены и правила визуала | [[{design} linkedin]] |
| session | `sessions/` | конспект запуска агента: задача, токены, тронутые файлы | пишется после первого запуска из консоли |

Ещё три ветки не вошли в двенадцать: `context/` (правда о продукте), `research/` (внешние сканы) и `guides/` (инструкции для людей). Они читаются как справочный слой и в цепочке «источник → результат» не участвуют.

## 7 связей
| связь | от → к | как записана | пример |
|---|---|---|---|
| `derived_from` | nucleus → source; output → nucleus | поле `source:` у нуклеуса, поле `nucleus:` у черновика | n02 → конспект занятия; li-01 → n02 |
| `uses` | skill → rule, tool, design | ссылка в теле скилла | [[{skill} linkedin-post]] → [[{rule} anti-slop]], [[{design} linkedin]] |
| `checks` | gate, eval → output, rule | ссылка в файле проверки или отчёта | [[{eval} scorecard – 2026-09-29]] → черновики пачки |
| `owns` | role → skill, automation, outputs | ссылка в разделе «зона» роли | [[{role} marketer]] → [[{automation} weekly loop]] |
| `calls` | automation → skill | строка «скилл» в паспорте рутины | [[{automation} weekly loop]] → [[{skill} weekly-loop]] |
| `renders` | tool, skill → output | путь рендера в теле дизайн-файла | [[{design} carousel]] → `{carousel} car-01 weekly loop.html` |
| `touched` | session → любой файл | ссылки в разделе «файлы» сессии | сессия автора → [[{post} li-01 fake winner]] |
| `learns_into` | eval, dashboard → rule, skill, golden set | раздел «что происходит с находками» | недельный срез → строка в [[{rule} anti-slop]] и пример в [[{eval} golden-set]] |

Поля frontmatter (`source`, `nucleus`) читаются машиной напрямую. Остальные связи лежат обычными вики-ссылками в теле файла: инструмент читает их теми же глазами, что Obsidian.

## одна цепочка целиком
```
kumar creative machine → n02 fake winner → li-01 → scorecard → weekly – 2026-09-29 → anti-slop · golden-set
source                   nucleus            output   eval        dashboard              rule · eval
```
Четыре звена: `derived_from` (дважды), `checks`, `learns_into`. По цепочке идут вперёд, когда пишут текст, и назад, когда проверяют цифру: пост → нуклеус → источник и таймкод.

## id живёт во frontmatter
У сущности, на которую ссылаются часто, во frontmatter стоит `id`: `id: n02`. Имя файла может меняться при правке: название, дата, порядок слов. Ссылки по `id` остаются на месте, граф не рвётся. Пока файл ищут по имени, каждое переименование создаёт в графе второй узел и оставляет первый висеть без связей. В наборе `id` есть у нуклеусов, код креатива `P1-H3-A1-F1` играет ту же роль для черновиков. Переименование делается в Obsidian: ссылки обновляются сами ([[{rule} naming]]).

## как инструмент рисует связи
Инструмент `marketing-harness-sim` читает все файлы набора, вытаскивает вики-ссылки и пути в обратных кавычках и проводит между файлами линию. Цвет узла показывает слой. Агент, который работает с файлом, зажигает узел, файлы, которые он записал, получают яркие линии. Нуклеус без входящей линии от источника виден сразу как одинокая точка, скилл без исходящих линий к правилам – как скилл, который правила не читает ([[{guide} nuclei]], раздел про стрелки).

Проверка графа руками: открой файл в Obsidian, в правой панели «Backlinks» показаны все, кто на него ссылается. Пустая панель у правила означает, что правило не подгружает ни один скилл.

## как устроено у команды AI Mindset
Команда держит рабочий волт как трёхслойную память. Нижний слой – сырьё: транскрипты, выгрузки, письма, неизменяемые свидетельства. Средний слой делится на знание («что верно») и события («что случилось»). Верхний слой – рабочая память («что делать дальше»), она затухает: пункт без свежего подтверждения уходит из выдачи. У каждого факта стоит источник и уверенность (высокая, средняя, низкая), поэтому ответ агента можно проверить обратным ходом до файла.

Раз в сутки ночная сборка проходит по волту, вынимает из каждого документа факты и складывает их в базу. Тип файла в имени – `{rule}`, `{process}`, `{decision}`, `{meeting}` – заменяет ручную разметку: сборщик читает его как вид сущности. Две вещи стоят на виду в командной практике: переименование файла в такой сборке создаёт второй документ, а отменённое решение хранится отдельным графом решений и по умолчанию скрыто из ответов.

Двенадцать типов набора ложатся на эту таксономию без переименований. Папку харнесса можно позже отдать в такую сборку: `{source}` станет сырьём, `{nucleus}` и `{rule}` знанием, `{dashboard}` и недельные строки рабочей памятью.

## куда расти
1. **Завтра.** Пройти по своей папке и назвать тип каждого файла. Файл без типа или в чужой папке переезжает ([[{rule} principles]]).
2. **Неделя.** Добавить `id` во frontmatter всем нуклеусам и обратные ссылки от черновиков к ним. Открыть граф и найти одинокие точки.
3. **Месяц.** Ввести статус нуклеуса `reuse`, `refine`, `archive` и обновлять его в недельном срезе ([[{guide} nuclei]]).
4. **Дальше.** Завести восьмую связь под свою задачу (`approved_by`, `published_to`), записать её в этот файл и в [[{rule} principles]] одной строкой. Новая связь нужна, когда без неё нельзя ответить на вопрос, который ты задаёшь каждую неделю.
