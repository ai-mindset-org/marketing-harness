# harness-principles

аудит папки по 14 принципам из [[{rule} principles]] и по восьми практикам, проверенным на командном харнессе AI Mindset. читает всё, правит ничего: отчёт получает человек, правки идут через [[{skill} harness-evolve]].

## часть 1 · четырнадцать принципов
по каждому принципу – проверка одной командой или взглядом.
| № | принцип | проверка |
|---|---|---|
| 1 | папка – интерфейс | нет решений, которые живут только в чате: сверь последние решения с `rules/` и `context/` |
| 2 | роутер короткий | `wc -l AGENTS.md` до 80 строк; детали в скиллах |
| 3 | один источник на факт | одна и та же цифра встречается в одном файле; `.claude/skills` совпадает с `skills/` (запусти `node bin/sync-skills.mjs`, `git status` не показывает новых правок в зеркалах) |
| 4 | четыре слоя | у каждого нового файла ясен слой: правило, скилл, инструмент, eval |
| 5 | у ветки один писатель | по `git log --format=%an -- <папка>` видно, что в `context/` и `rules/` пишет человек |
| 6 | файлы передачи | цепочка `sources/ → nuclei/ → outputs/ → evals/ → dashboards/` без пропусков |
| 7 | у правила есть проверка | каждое правило в `rules/` имеет строку в [[{eval} checks]] или пример в [[{eval} golden-set]] |
| 8 | ошибка дважды – правило | «выучено на ошибках» в [[{rule} anti-slop]] непусто и совпадает с golden set |
| 9 | сообщённое, а не сгенерированное | `node bin/check.mjs` без `факт?` в утверждённых файлах |
| 10 | человек публикует | нет статуса `published` без предшествующего `approved` |
| 11 | ключи вне папки | `gitleaks detect` чисто; `.mcp.json` ссылается на `${ИМЯ}` |
| 12 | коммит на шаг | `git log` – по коммиту на прогон, сообщение называет роль |
| 13 | имя читается | все файлы по [[{rule} naming]]; исключения только README, AGENTS, CLAUDE, `bin/` |
| 14 | минимум на старте | нет инструментов без задачи: каждый файл в `tools/` вызывается хотя бы одним скиллом |

## часть 2 · практики командного харнесса
| практика | что проверить | почему |
|---|---|---|
| машинное происхождение | во frontmatter файлов агента: `generated_by`, `generated_at`, `human_verified: false` | видно, кто написал и проверил ли человек |
| отдельная папка черновиков агента | сырые итерации живут в личной папке оператора, в общей лежит результат | общая папка не зарастает вариантами и копиями |
| тип в имени файла | все файлы имеют `{тип}` в начале | машина и человек фильтруют по имени |
| проверка секретов перед коммитом | хук или команда `gitleaks detect` перед `git push` | утёкший ключ отзывают, лучше не допустить |
| один планировщик и один владелец | у каждой автоматизации в [[{guide} automation]] заполнены оба поля | двойной запуск и бесхозная рутина |
| скиллы из одного источника | правка идёт в `skills/`, зеркала пишет скрипт | зеркала расходятся молча |
| файл передачи контекста | при конце сессии агент пишет краткий файл: что сделано, что открыто, где остановился | следующая сессия начинается без пересказа |
| очередь подтверждения человеком | список файлов с `human_verified: false` в порядке возраста | видно, сколько работы агентов ждёт глаз |

## порядок работы
1. прочитай [[{rule} principles]] и [[{rule} naming]].
2. пройди часть 1 сверху вниз, запиши результат по каждой строке.
3. пройди часть 2, там где проверка требует команды, запусти её и запиши вывод одной строкой.
4. по каждому «нет» предложи минимальную правку: файл, строка, команда.
5. отчёт запиши в `evals/{eval} scorecard – <дата>.md`, блок «аудит харнесса».

## формат отчёта
```
принцип или практика · да/нет · где · что поправить
2 · роутер короткий · нет · AGENTS.md, 112 строк · вынести таблицу скиллов в README
11 · ключи вне папки · да · .mcp.json ссылается на ${EXA_API_KEY} · –
```
итог одной строкой: сколько «да» из 22, три самые дорогие правки. срочными считаются пункты 10 и 11: публикация без человека и ключи в git.

## границы
правила и контекст не правь, предлагай правку человеку. персональные данные и содержимое ключей в отчёт не попадают: указывается только файл и строка.

## когда проверить нельзя
- нет `.git` (копия папки без истории) или не установлен `gitleaks` – пункт получает «не проверено» с причиной, в счёт «нет» не идёт;
- в итоге три числа: да · нет · не проверено.
